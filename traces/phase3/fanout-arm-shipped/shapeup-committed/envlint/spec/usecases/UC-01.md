# Use Case: Lint Env File

## Summary
A developer (or CI pipeline) runs `envlint --schema <schema.json> [--json] <envfile>`, and the
tool reports every way `<envfile>` violates `<schema.json>`, or confirms it's clean, then exits
with a status code CI can branch on.

## Preconditions
- Both the env file path and the schema file path are given explicitly as CLI arguments — no
  implicit lookup of the caller's own `.env` (this is the constraint that makes the tool
  fixture-testable; see idea.md).
- `--schema` must be present; its absence is itself a tool error (E_NOFLAG), not a usage no-op.

## Input

```typescript
interface LintEnvFileInput {
  schemaPath: string;   // from --schema <path>, required
  envPath: string;      // the single positional argument, required
  json: boolean;         // presence of --json flag, default false
}
```

## Steps

```
1. Parse argv: --schema <path>, optional --json, one positional <envfile>.
   Missing --schema -> E_NOFLAG, exit 2 (stop; nothing else runs).
2. Read the schema file (node:fs). Missing/unreadable -> E_SCHEMA_UNREADABLE, exit 2.
   Parse as JSON. Invalid JSON -> E2, exit 2.
3. Read the env file (node:fs). Missing/unreadable -> E1, exit 2.
4. Parsing engine: parseEnv(envText) -> { pairs, problems }.
   - Comments (`# ...`) and blank lines are skipped, produce neither pair nor problem.
   - `export KEY=value` is equivalent to `KEY=value` (the `export` prefix is stripped before
     the rest of parsing, including quote-stripping -- so `export KEY="value"` strips both
     the prefix and the quotes).
   - `KEY="value"` / `KEY='value'` strip matching surrounding quotes only; `KEY="value` (no
     closing quote) is left untouched, quote included in the value.
   - Whitespace around KEY and around the value is trimmed (outside quotes).
   - A line that is not blank/comment/`[export] KEY=VALUE` -> a ParseProblem at its 1-based
     line number, raw text kept verbatim for later truncation.
   - Every occurrence of a repeated key is kept, in file order (dedup is a Rules-time concern,
     not Parsing's).
5. Rules engine: evaluate(pairs, problems, schema) -> Finding[].
   - Each ParseProblem becomes one Finding: key = raw line text truncated to 30 chars,
     message = "not a KEY=VALUE assignment", line = the problem's line (E4).
   - For duplicate keys, only the LAST occurrence in file order is evaluated against the
     schema -- the earlier occurrence(s) produce no finding of their own (INV-02). If the file
     has zero assignments at all (E3: empty, or only comments/blanks), every `required` schema
     key is reported missing (line 0), and the run must NOT print `ok` even though there are
     no parse problems.
   - A key present in the file but absent from the schema -> never a finding (INV-01).
   - required + absent from file entirely (after dedup) -> Finding, line 0.
   - type/enum checks run only against the winning value for keys present in the file; a
     present-but-empty value (`KEY=`) satisfies `string`, fails `int`/`bool`/`url`/`enum`.
   - `url` type: must both parse via `new URL(v)` AND have protocol `http:` or `https:` --
     parsing alone (e.g. `ftp://x.com`, `mailto:a@b.com`) is not sufficient (confirmed by
     spike-url-type-validation.md).
6. CLI composes LintReport { ok: findings.length === 0, findings, checked: Object.keys(schema).length }.
7. CLI renders LintReport per --json:
   - human: "ok: N keys checked" (clean) OR one line per finding + "N problem(s)" (findings).
   - --json: exactly one JSON document {"ok","findings","checked"} on stdout, nothing else.
8. CLI exits 0 (clean) or 1 (findings) -- exit code is unaffected by --json.
```

## Output

```typescript
interface LintEnvFileOutput {
  exitCode: 0 | 1 | 2;
  // exitCode 0 | 1 branches:
  report?: { ok: boolean; findings: Finding[]; checked: number };
  // exitCode 2 branch (report is never produced):
  errorMessage?: string; // stderr, prefixed "Error: ", single line, no stack trace
}

interface Finding {
  line: number;   // 1-based, or 0 when there is no source line
  key: string;
  message: string;
}
```

## System Flow

```
[CLI: bin/envlint.mjs argv]
  → [Use Case: Developer.lintEnvFile()]
    → [fs.readFileSync(schemaPath)] / [fs.readFileSync(envPath)]
      → [Parsing.parseEnv(envText) -> {pairs, problems}]
        → [Rules.evaluate(pairs, problems, schema) -> findings]
          → [CLI composes LintReport, renders per --json, sets process.exitCode]
```

No persistence, no network call, no domain event — this UC starts and ends within a single
process invocation (matches project-profile.md: no server, no listener).

## Invariants

- [INV-01] A key present in the env file but absent from the schema is never a finding.
- [INV-02] When a key is assigned more than once, the later assignment wins; only the winning
  value is evaluated against the schema, and the earlier assignment(s) produce no finding of
  their own — even when the earlier value would itself have been valid and the winning value
  is not (or vice versa).
- [INV-03] Exit code is exactly one of `0` (clean), `1` (≥1 finding), `2` (tool could not run) —
  never any other value, never a thrown/uncaught exception surfacing a stack trace.
- [INV-04] `--json` changes only the rendering of the non-error branches (exactly one JSON
  document on stdout, nothing else on stdout); it never changes which branch is taken or the
  exit code.
- [INV-05] Every exit-2 message is written to stderr, prefixed `Error: `, as a single line —
  never a bare stack trace, regardless of which of E1/E2/E_NOFLAG/E_SCHEMA_UNREADABLE fired.
- [INV-06] E3's "must not report ok" applies to the case that motivates it: an env file with
  zero assignments AND >=1 `required` schema key, which guarantees >=1 finding and so exits 1.
  When the schema has zero `required` keys, a zero-assignment file produces zero findings, and
  EXPECTED.md's own literal exit-code rule ("exit 0 — no findings") governs: it exits 0 and DOES
  print `ok: N keys checked`. This reading is pinned by a fixture (TS-INV-06) rather than left
  inferred, since EXPECTED.md's E3 wording alone could be misread as an absolute "never ok".

## Error Cases

| Error Code | Condition | Exit Code | Handling |
|---|---|---|---|
| `E_NOFLAG` | `--schema` not given | 2 | stderr `Error: ` + reason, no schema/env file is read |
| `E_SCHEMA_UNREADABLE` | schema file missing or unreadable | 2 | stderr `Error: cannot read schema file: <path>` |
| `E2` | schema file is not valid JSON | 2 | stderr `Error: schema is not valid JSON: <path>` |
| `E1` | env file missing or unreadable | 2 | stderr `Error: cannot read env file: <path>` |
| `E3` | env file has zero assignments (empty / only comments+blanks) | 1 or 0 | every `required` key reported missing (line 0); exit 1 if that produces >=1 finding, else exit 0 with `ok` (see INV-06) |
| `E4` | a line is not blank/comment/`[export] KEY=VALUE` | 1 | finding `<file>:<line>: <line text truncated to 30 chars>: not a KEY=VALUE assignment` |
| `E5` | (not an error — output contract) `--json` output shape | 0/1 | exactly one JSON document, no other stdout output |
