# Changelog for coach

| Version | Date | Changes |
|---------|------|---------|
| 0.5 | 2026-08-02 | **ADR-0001 consumer layout** (unreleased). The knowledge base moves with the shared root: `shapeup/knowledge-base/<skill>.md` and `shapeup/knowledge-base/harness-defects.md`, the gitignored run-trace root is `.shapeup/`. ADR-0001 names this an explicit **exception** to its own rule (structured policy would otherwise be local): coaching rules describe how an agent should work *in this codebase*, which is a team property even when every run is individual — so the KB stays committed while `gate-answers.json` and `safety-overrides.json` deliberately do not, since no committed file may widen another person's consent or safety envelope. Nothing about the coach's behaviour changed; the reason it writes where it writes is now written down. |
| 0.4 | 2026-07-14 | **Domain-layer alignment** (v1.1.0). Documented the envelope contract: orchestrated dispatch is WorkOrder in (`--order`) / WorkResult out like every worker; standalone flags map 1:1 onto the payload fields registered in `domain.schema.json` (`x-payload-by-worker`), and output fields follow `x-result-by-worker` — the KB files return as `files_touched`/`artifacts`, the coach itself remaining a direct writer of its own committed substrate. No behavior change. |
| 0.3 | 2026-07-13 | **`harness-defect` — a fourth answer at GATE COACH-1** (v0.5.0), beside the three coachable skills and `skip`. Feedback whose root cause is the mechanism itself (a fail-open hook, a gate reading the wrong file, contradicting skill contracts) was previously force-fit into a worker's KB, which teaches a worker to compensate for a defect instead of fixing it. The PO can now categorize it `harness-defect`; the coach files it to the committed defect register (`knowledge-base/harness-defects.md`) as a drafted raw idea for the Betting Table — durable and PO-visible, **read by no worker**, never steering. Step 3's merge pass also reclassifies wrong-premise KB rules into the register rather than re-teaching them (KB-BA-002 was exactly this class: a PA3/gate defect filed as BA steering, on a premise `task-executor` v1.2 and `tech-lead` v0.5 contradict). |
| 0.2 | 2026-06-23 | **Team-shared, read-back knowledge base** (v0.2.5). Each guideline is filed by skill under the **committed** `knowledge-base/<skill>.md` — shared on `git pull` — instead of one flat, gitignored file that was never read back. New **GATE COACH-1** asks the PO which skill each rule belongs to and never assumes. Read-side hooks land in the same release: `task-executor` (Phase 1), `ba-pitch-analyzer` (Phase 1) and `qa-edge-hunter` (Phase Q1) each load their own file at the top of a run. `spec-evaluator` is deliberately **not** coachable — the single-judge rule makes the KB guidance, never an invariant. Ships with an idempotent, non-destructive migration that moves an old flat KB across, preserving its rules into `_INBOX.md` for categorization rather than auto-assigning them. |
| 0.1 | 2026-06-19 | Initial RLHF loop. Ingests raw Product Owner / Tech Lead feedback from the Ship Sign-off (GATE L4) and turns it into structured guidelines future runs read back; `tech-lead` invokes it automatically when the PO gives substantive feedback instead of a bare `y`. Not a grader (`spec-evaluator`), not a fixer (`task-executor`), not the discovery ledger. |
