Most of a mobile test surface should never touch the UI

Grading a use case needs exactly two probes: one that proves a user can reach it, and one that proves it happened. Everything the planner derives about validation belongs at the API layer — and mobile is simply the platform that makes you notice. Rev. 4 is the implementation form: the argument checked against the harness that has to run it, the mobile route's exception replaced by a directive, and the whole of it organised into skills that already exist.

Why two probes, and not one

Grade "did the use case happen" by side effect alone and this passes: a checkout screen whose Pay button is wired to nothing, while the payment engine works correctly and gets exercised through a deep link. Order row present, payment call correct, verdict green — and no user can ever pay. That is the orphaned engine: the defect the wiring map and solution-architect's entire remit exist to prevent, and the most common shape of machine-written code — engine correct, call site missing.

So outcome and affordance are not substitutes. Outcome grades the engine; affordance grades the wiring. The affordance evidence needed to close the hole is far smaller than "validate the screen" — it is one id:

drive the entry affordance (one id per UC — proof of reachability) → assert the outcome (data / network / log — proof of behaviour)

The wiring map already carries exactly this shape, one row per use case: use_case | engine | wiring_seam | entry_call_site | affordance, and the affordance column is already singular. The ask on a Flutter or native team is therefore one stable id per use case, not an instrumented UI.

The wiring map carries the shape; the evaluation contract does not. A criterion carries one oracle and each runner's expectation grammar is closed, so "drive here, assert there" has nowhere to live on a row today. That gap is phase B′, below.

The routing rule

Pick the oracle from where the behaviour is decided, not from what the user touches.

The rule it replaces — pick from the deliverable type — routes every derived row on a mobile deliverable to ui, which is also the default when the tag is absent. But D3 derives missing-field, type-violation and boundary rows: validation, decided at the API, not the screen. You do not drive a phone to prove that amount: -1 is rejected; you send the request, and the http oracle answers in milliseconds instead of walking an accessibility tree that measured ~4,700 ms per dump on a warm Android emulator.

Two cells carry a rev. 4 warning. data is not a dispatch key — D1's persistence assertion rides inside the http row's evidence until a runner is registered. mobile is named here for where phase D lands it; writing it on a row before the runner exists produces an exception at grading time, not a FAIL, so the tag is a plan, not an instruction.

D5 is a real gap, not a re-labelling — with one qualification rev. 3 skipped. D1–D4 derive from invariants, error tables, contract shapes and no-gos — none of which can express "the user can actually get here". The wiring map holds that fact and the Test Surface never consumes it. The qualification: harness verify trace already runs a reachability oracle at L1b that proves each engine is reached from entry_point through the import graph. So the orphaned engine is half-caught already, statically. D5 is the runtime half — the half that notices a live import path behind a dead button.

D5 also has a sequencing problem. Its source is wiring-map.md, whose sole writer is solution-architect at GATE L1a.5. The Test Surface is derived by ba-pitch-analyzer's analyze operation, which runs at L1a — before wiring, because wiring needs its use cases. At the generation point where D1–D4 are written, D5's source is guaranteed absent. Either D5 belongs to a retrofit-surface pass after L1a.5, or it needs the harness's standing absent-artifact rule stated on it: no wiring map ⇒ the arm is skipped, never silently empty. And the id needs a discriminator — TS-REACH-<UC>, since every other rule carries one and "one per use case" otherwise collides on the first two.

The web case hid this design question because the DOM is cheap, so nobody noticed that API validation was being asserted through a browser. Mobile charges you for the tree and the mis-routing becomes visible. Fixing it improves the web contract too — those rows are slower and flakier through Playwright than through fetch as well.

Where this does not reach: a use case whose point is visual — a control that must be disabled, an error the user must read. Those still need tree assertions. The UC's own ## Steps say which, so it is a per-UC judgement, not a ratio worth inventing.

How a row actually gets graded

The routing rule decides which tag a row carries. What happens next is a single mechanism, and it is worth drawing, because two of this document's problems are visible in it and invisible in prose: where the mobile lane terminates, and where a citable artifact comes from.

The row shape the two-probe thesis needs

Follow the diagram back up and the contract problem is obvious: the fan-out is one-per-row. "Drive the affordance, assert the outcome elsewhere" wants two runners under one verdict, and the cheapest way to say that is a second, subordinate assertion on the same row — the affordance half proves reachability, the assert half proves behaviour, and the pair grades as one: 

{ "id": "TS-REACH-UC-03", "oracle": "ui",
  "probe":  { "path": "/cart", "steps": [ { "click": "checkout-submit" } ] },
  "expect": { "url": "/checkout/success" },

  "then_assert": {                        // ← phase B′: the second probe, a different runner
    "oracle":  "http",
    "probe":   { "path": "/api/orders?last=1" },
    "expect":  { "status": 200, "json": { "state": "created" } }
  } }

This keeps every property the registry already has — each half is graded by its own runner through the same {fails, results} interface, each half's grammar stays closed, and the row still yields exactly one verdict and one citation. It is also what makes D5 affordable on mobile: the expensive half stays one tap, and the assertion never touches the device.

The mobile route returns a plan, not an exception

Throwing is indefensible on its own terms: everywhere else in this harness a missing tool is a NO EVIDENCE row naming the fix, and only the mobile lane crashes. But the tempting repair — hand the judge the row and let it work out how to verify — is worse than the crash, because it reinstates exactly what the ui oracle was built to end: a verdict narrated by the model, with no artifact to hash, nothing for the seesaw to replay, and the affordance rule reduced to prose addressed to the same model the anti-leniency protocol exists to distrust.

The judge may choose how to look. It may never say what it saw.

So the mobile route degrades into a probe plan: a directive carrying facts read off the machine, and a response schema whose output is a list of actions — each one executed by a runner that is already in the registry. The model picks the probes; the runners produce the evidence; the verdict is derived from that evidence exactly as it is for every other oracle. Nothing about the single judge, the T0 citation or the ratchet changes.

The facts block is what makes the plan honest

A prompt asking a model to "find a way to verify this" gets a plausible answer whether or not a way exists. The directive removes that degree of freedom by stating, exhaustively, what is present — stack detected from the files that identify it, resolvable CLIs with versions, booted devices, the project's own test command, whether a web target exists — and declaring the list closed. An action naming anything outside it is rejected by a check, not by good intentions.

The response schema, and the four things it forces

The plan is one JSON object. Every action maps onto a runner's existing contract shape, so nothing needs translating on the way in: 

{ "row_id": "TS-REACH-UC-03", "stack": "expo",
  "actions": [
    { "id": "web-affordance", "kind": "ui_web", "tier": 2, "proves": "reachability",
      "why": "Drives the checkout entry affordance on the web target.",
      "target_note": "Expo web target only — not evidence about the native build.",
      "server": { "cmd": "npm run web", "ready_path": "/" },
      "probe":  { "path": "/cart", "steps": [ { "click": "checkout-submit" } ] },
      "expect": { "url": "/checkout/success" } },

    { "id": "order-created", "kind": "http", "tier": 1, "proves": "outcome",
      "why": "Asserts the outcome where it is decided — the order row.",
      "server": { "cmd": "npm run api", "ready_path": "/health" },
      "probe":  { "method": "GET", "path": "/api/orders?last=1" },
      "expect": { "status": 200, "json": { "state": "created" } } } ],

  "coverage": { "reachability": "web-affordance", "outcome": "order-created" },
  "rejected_cheaper_tiers": [
    { "action": "web-affordance", "skipped_tier": 1,
      "reason": "No tier-1 probe can observe whether the entry control is wired." } ] }
1
A verdict cannot be expressed
No pass, fail, score or confidence property is declared anywhere, and additionalProperties is false at every level — so the model cannot smuggle one in, and the check reports the exact path when it tries.
2
Both probes must be answered for
coverage is required and has both keys. A null obliges a reachability_gap_reason naming what is missing. This is the schema enforcing the one rule this document says must never be quietly dropped — outcome-only grading.
3
There is no mobile action kind
A resolvable mobile driver is precisely the condition under which no directive is written, so the plan is expressed entirely in runners that exist today. The consequence is the useful one: a Maestro or Argent flow reaches the harness as a process action — it exits with a status code, which process already grades and the ratchet already cites. Phase D stops being a precondition and becomes an optimisation.
4
manual is an admissible answer, and that is the point
The pressure that makes a model invent a command is having no legal way to say "there isn't one". A manual action carrying a reason and repeatable steps is schema-valid and surfaces at sign-off. Two rejected plans in a row collapse the row to NO EVIDENCE — no admissible probe plan, which is the same honest shape as a missing browser.

Three rules the schema cannot express are applied after it passes, and they are the teeth: every id named in coverage must exist in actions; stack must echo what was detected; and the head of every command is cross-checked against the resolvable-CLI list. That last one is what a plausible-sounding invented tool dies on.

The template, the schema, a worked Expo plan and three negative controls are drafted alongside this document, with a zero-dependency checker that runs them: the worked plan is accepted, a plan omitting reachability is rejected for the missing gap reason, a plan carrying a pass field is rejected at that property, and a plan invoking maestro on a machine without it is rejected by name. A checker that accepts everything would be worse than none, so it ships its own controls.

The precondition is a probe, not a taxonomy

Argent drives an installed app through the OS — its own agent docs classify a project as React Native, Expo, Flutter, native iOS or native Android and state it "provides environment context regardless." So the driving layer is source-agnostic, and an earlier revision's four-stack governance machinery — a schema field, a wiring-map contract and a spec-lint rule per stack — was the wrong shape.

What varies is not the stack. It is whether this build exposes what the wiring map claims. Ask the running app, not the schema: 

launch → resolve each entry affordance the wiring map names

  none resolve      → every D5 row FAILs: "unverifiable — the build exposes no
                       addressable entry affordance", plus the stack's fix line.
                       A wiring defect, which is how the harness already treats
                       an untestable AC.

  this UC's absent  → that UC's D5 row FAILs, localised to the missing id.

  resolves          → drive it, then assert the outcome.

This is stronger than a spec-lint rule for a reason that matters: a wiring map can claim an identifier the built app does not expose. The probe reads the app. And what remains stack-specific is four strings — the fix line: Semantics(identifier:) for Flutter, accessibilityIdentifier for iOS native, testID for RN/Expo, android:id for Android native.

Phase E — landed, and not yet correct

The ui oracle queries the DOM; a Flutter Web app renders into one <canvas>, so getByTestId matches nothing and the result is a wall of plausible FAILs whose real cause is that there is no DOM to query. The guard that landed is wrong twice: it throws inside the per-criterion driver, so it reports as a behavioural FAIL and sends the fixer at application code that is fine — where the missing-browser path it was told to copy returns failAll(criteria, "NO EVIDENCE — …"); and its test, body.children.length === 1, is defeated by a <script> in the body, which Flutter's own web template puts there. Rework: the refusal path the oracle already has, keyed on no addressable semantics anywhere plus a canvas host at any depth, with the canvas-only fixture that turns "it works" into something a suite asserts.

The one cell to test before relying on it — 30 minutes

Argent's reference says its iOS-simulator runner resolves against the native UIView hierarchy ("the runner derives the role from the view class"), while its describe tool reads the accessibility tree. A Flutter app on iOS is essentially one UIView; its semantics live as accessibility elements, not views. So Flutter + iOS simulator is the single cell where source-agnosticism may not hold — on Android it should, because there the runner reads the full accessibility hierarchy, which is where Semantics(identifier:) lands.

A risk, not a finding: I did not run it. One Flutter screen with a Semantics(identifier:), one assert step, both platforms. If iOS fails, Maestro covers that cell and the driver field exists so the swap costs nothing.

What the harness already copes with, before a mobile oracle exists

"Can it grade a mobile project today?" has a better answer than no, and Expo is the clearest case. An Expo codebase does not present one ungradeable surface; it presents four, and three of them are already covered by runners that ship. The routing rule is what makes that true — once validation stops being asserted through a screen, most of the surface stops caring which platform draws the screen.

The ui oracle needs no change for the first lane. expo start --web renders through react-native-web into an ordinary DOM served over HTTP, which is precisely the shape the oracle already starts on a free port and drives. React Native's testID is forwarded by react-native-web as data-testid — the attribute page.getByTestId reads — so the affordance grammar carries over unchanged. That last sentence is the one cell to check before leaning on it: one Expo screen, one testID, one ui contract, thirty minutes — the same discipline this document already applies to Flutter on the iOS simulator, and for the same reason.

The same reasoning degrades gracefully rather than uniquely for Expo. A bare React Native project loses the web lane but keeps http and test. A Flutter project keeps both too, and its web target is the canvas case phase E exists for. What varies across stacks is one lane out of four — which is the strongest argument in this document for building phase B before phase D, and for not building a second evaluator at all.

Where a driver slots in

QA needs no driver at all. The hunter is exploratory and model-in-the-loop and issues no verdict — findings are born ~ with a repro — so it needs no stable selectors. "I backgrounded the app mid-save and the record duplicated" is a valid finding on Flutter, RN and native alike. What it does need is an order it can accept: GATE Q0's hard check is a request at app_url or an invocation of the entry point, and a phone is neither.

EVAL needs one, and only for D5. A driver taps one entry affordance per use case; it carries none of the validation rows, because those went to http. That is why the mobile oracle can be small — launch, resolve one id, tap, hand off to the outcome probe.

Argent's flow run and Maestro's test both replay YAML without an LLM in the loop and exit with a status code, so a flow is a valid T0 fixture: hash-citable, seesaw-replayable, and it moves the ratchet's score. That property is what makes either an oracle candidate at all — and it is also why a flow needs no oracle to be useful, since process already grades an exit code.

One judge, many oracles — not one skill per platform

The obvious-looking alternative is a spec-evaluator and a qa-edge-hunter per platform, each detecting its own stack. It is the wrong seam, and the diagram above already shows why: the fan-out belongs below the judge, in a registry built for it, not above the judge in the skill roster.

Two costs the left panel understates, both structural rather than stylistic:

  • Two judges is a broken invariant, not a duplicated file. "The verdict belongs to spec-evaluator" is what makes the verdict ledger mean anything; a second evaluator is a second opinion with equal standing, and nothing in the harness arbitrates.
  • Coaching forks silently. The retro writes committed rules to knowledge-base/<skill>.md, keyed by skill. A rule the PO teaches the web hunter never reaches the mobile one — divergence in exactly the artifact built to accumulate.

The next section is this claim made checkable: the whole of this document, organised into the skills that ship, and what the roster does when you apply it.

How the skills reorganise to carry this

One rule decides where every piece of platform knowledge lands, and it falls straight out of the precondition argument above:

A declared archetype steers the skills. A detected stack steers the oracle. Neither is ever a branch inside a SKILL.md.

The archetype is written at GATE L0 into project-profile.md and validated against a five-value enum — a typo must FAIL rather than silently disable reachability — so planning-time choices key off it. The stack is a fact about this build on this machine, so probe-time choices key off detection instead, inside the oracle where no model is involved.

The schema change, in full

+                  "device_target"     // nullable {binary, device_id}; archetype comes from the profile

A probe plan is not a WorkResult field. It is an oracle artifact under the gitignored tier — .shapeup/<feature>/eval/directives/ — alongside the directive that asked for it. So the single-judge invariant is held by the schema rather than by convention: no worker can return a verdict through the directive channel, because x-result-by-worker declares no such field for anyone but the evaluator.

The guards, without which none of this is worth landing

  • The registry↔prose parity check becomes bidirectional, and lands first, red — so it demonstrably catches the two phantom oracles before the runner that legitimises one of them exists.
  • plan-check.mjs runs its own negative controls in CI: a plan omitting reachability, a plan carrying a pass field, a plan invoking a CLI the facts block does not list.
  • A canvas-only fixture the Flutter Web guard must catch, paired with a normal DOM page it must not.
  • The new references/ files inherit the dangling-path check for free — it already walks every skill's references directory.
  • A line ratchet on qa-edge-hunter once it is cut, lowered with the reason inlined in the check, the way the orchestrator's was — a lowered ratchet whose justification lives elsewhere is indistinguishable from one somebody weakened.

Its first day of remaining work is not new capability at all: it is the sweep that stops the evaluator penalising the rows the new rule tells the planner to write, and the parity check that would have caught two oracles being named before they existed. Ship that before anything on this page is measured.

What deliberately not to do

  • Do not grade a use case by outcome alone. It is the tempting simplification and it silently retires the orphaned-engine check. One reachability probe per UC is the price of keeping it.
  • Do not assert API validation through the UI, on mobile or on the web. It is slower, flakier, and it tests the form rather than the rule.
  • Do not let a Flutter team use Key for test targeting. It is invisible to the accessibility bridge and therefore to every external driver — and the entry-affordance probe is what catches it, on the running build, with no declaration to trust.
  • Do not add either tool's MCP server to the harness. Same shape as the Playwright MCP dependency already removed: streams the tree into context, costs tokens per probe, narrates a verdict instead of exiting with one. It belongs to the developer's own agent session.
  • Do not enable visual regression on any stack, however good the tooling. Layer-3 styling is frozen; a judge grading typography drift resurrects the freeze through the back door.
  • Do not build one oracle per stack. One grammar, one driver field.
  • Do not build one evaluator or one hunter per platform either. The platform fan-out belongs in the registry, below the judge. Above it, it breaks the single-judge invariant, forks the coached knowledge base, and doubles a roster entry to buy a D5 lane.
  • Do not let the directive return a verdict. The moment a probe plan is allowed to carry a pass, the mobile lane becomes the one place in the harness where the judge grades its own narration — which is the property the ui oracle was built to remove, and it would be removed by accident rather than by argument. The schema must have no such field to declare, and the checker must report the path when one appears.
  • Do not let the plan invent a tool. An action naming a CLI absent from the directive's facts block is rejected by name, not tolerated and retried. The pressure that produces an invented command is having no legal way to say "there is no way to do this" — which is exactly why manual is schema-valid and why removing it would make the plans worse, not stricter.
  • Do not name an oracle in the prose before its runner is registered. The parity check walks registry → prose only, so the reverse passes a green suite and the first thing to meet the phantom tag is the evaluator, at grading time, with an exception where a verdict should be. Land the runner and the row in the same change, or neither.
  • Do not read an Expo web-target pass as evidence about the native build. It is a genuine, cheap grade of D1–D4 and of D5 on that target. react-native-web and the native renderer can wire the same screen differently, so the row must say which target it drove.
  • Do not start at D. It is the most interesting phase and has the worst cost-to-value before B has cut the surface — a well-built oracle grading rows that should have gone to http.
  • HarmonyOS is out of scope here, deliberately. The same lens applies and the blocking question is the same one — whether the stack exports stable identifiers a driver can resolve — but it deserves a look at ArkUI's accessibility surface directly rather than by analogy.

What would change this

  • Argent cannot resolve a Flutter id on an iOS simulator. The UIView-hierarchy risk. Half an hour to settle; if it holds, phase D ships with maestro as the default driver on that cell.
  • The use cases have no API layer. An offline-first or fully local app has nowhere to route D1–D3, and the UI surface stays large. Then the tree cost is unavoidable and phase D matters more than phase B.
  • The wiring map is not populated. D5 derives from it; without it there is no entry affordance to probe and reachability goes back to being an assumption.
  • A team refuses the one identifier per use case. Then that use case is genuinely ungradeable for reachability by any tool, and the honest answer is [manual] for that row with the reason stated — not coordinate taps dressed as evidence.
  • No mobile pitch arrives. Phases B and E are still worth doing on their own: one improves every archetype's routing, the other closes a live defect.
  • react-native-web does not forward testID as data-testid. Then the Expo shortcut collapses to D1–D4 through http and test, the web lane stops carrying D5, and phase D moves ahead of F. Thirty minutes to settle, and worth settling before anyone plans around the web target.
  • Probe plans come back consistently unusable. If a schema-valid plan routinely names the wrong tier, covers only the outcome, or degrades to manual where an executable action existed, the directive is doing less than a fixed per-stack action table would — and a fixed table is the cheaper answer. The falsifier is measurable from the plan checker's own rejection log, which is why the log is part of C′ rather than an afterthought.
  • A data runner gets registered. Then D1 legitimately splits again — persistence assertions leave the http row's evidence and become their own probe. Until that runner exists, writing the tag produces an exception, not a verdict.
